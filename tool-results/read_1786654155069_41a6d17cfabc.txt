   103→   103→#### 3. Unresolved Issues / Risks + Next-Phase Recommendations
   104→   104→
   105→   105→**Minor risks (low priority)**:
   106→   106→1. **Voice input** depends on Web Speech API (Chrome/Edge only) — gracefully hidden on unsupported browsers. No change from Round 4.
   107→   107→2. **Interview timeline per-question time** is derived from history timestamps (includes API latency). Could be made more precise with a dedicated `secondsSpent` field on the answer record.
   108→   108→3. **PDF export** relies on the browser's native print dialog — the user must select "Save as PDF" as the destination. This is the standard, dependency-free approach but requires one user action beyond a direct download. A future enhancement could use `pdf-lib` or similar for direct download, but adds bundle weight.
   109→   109→4. **Bookmarks are localStorage-only** — they persist across sessions on the same browser but don't sync across devices. If cross-device sync is needed later, a `/api/bookmarks` route + Prisma model would be the path.
   110→   110→5. **Job templates are static data** — adding more templates (e.g., Security Engineer, SRE, Data Scientist, Engineering Manager) is a data-only change in `src/lib/job-templates.ts`.
   111→   111→
   112→   112→**Priority recommendations for next phase (P5+)**:
   113→   113→1. **Comparative analytics dashboard** — Track readiness improvement across multiple sessions with a trend chart (the comparison view exists but is one-shot; a dedicated progress-over-time view would be valuable).
   114→   114→2. **Interview replay player** — Step through the interview Q&A in a dedicated full-screen player with keyboard navigation (←/→ between questions), showing the question, your answer, the evaluation, and the detected gap that drove the next question.
   115→   115→3. **Custom competency weighting** — Let advanced users adjust the weights of readiness dimensions (Job alignment / Required coverage / Interview evidence / Technical readiness / Communication) and see their score recalculate live.
   116→   116→4. **Resume PDF parser improvement** — The current `extract-text` route handles .txt and simple PDFs; adding robust PDF parsing (pdf-parse or similar) would improve the upload experience.
   117→   117→5. **Question difficulty self-calibration** — Track which questions users tend to score low/high on and adjust the difficulty heuristic over time.
   118→   118→6. **Shareable public report link** — Generate a read-only public URL for sharing the assessment report with a mentor or hiring manager (would require a public session route + auth gating).
   119→   119→7. **Multi-language interview** — Let users pick the interview language (the LLM already supports multilingual output; the UI strings would need i18n).
   120→   120→8. **Calendar integration** — "Schedule a practice interview" button that creates a calendar event with the question set as a reminder.
   121→   121→
   122→   122→**Architecture notes for future agents**:
   123→   123→- The single-route `/` architecture (Zustand view state) is holding up well at 9 views + 3 modals. No need to refactor to multi-route yet.
   124→   124→- The `useSyncExternalStore` pattern introduced in `use-question-bookmarks.ts` is a good template for any future cross-component localStorage state (achievements, onboarding could be migrated to it for consistency).
   125→   125→- The print-report portal pattern (`createPortal` to `document.body` + `@media print` visibility swap) is reusable for any future "download as PDF" needs.

  1202→  1202→## Critical Bug Fix
  1203→  1203→
  1204→  1204→### AnimatePresence mode="wait" stuck at opacity:0 (CRITICAL)
  1205→  1205→
  1206→  1206→**Symptom**: When navigating to a view via `hydrateSession` (e.g., clicking a session in SessionHistory, or loading a URL with `#view=match&session=...`), the store correctly updated `view` to the target view, but the DOM showed the OLD view at `opacity: 0` — the motion.div was stuck in the EXIT state and the new view never mounted.
  1207→  1207→
  1208→  1208→**Root cause**: Framer Motion v12's `AnimatePresence` with `mode="wait"` has a bug where the exit animation completes (opacity reaches 0) but the exiting component never unmounts, and the new component never mounts. This was triggered specifically by the async `hydrateSession` flow — the view change happened after an `await fetch()`, which may have caused a timing issue with Framer Motion's internal state tracking.
  1209→  1209→
  1210→  1210→**Fix**: Replaced `<AnimatePresence mode="wait">` with a plain `<motion.div key={view}>` (no AnimatePresence wrapper). The `key={view}` forces React to unmount the old content and mount the new content immediately when the view changes. The `initial`/`animate` props provide a smooth fade+slide entrance animation. No exit animation (the old content is unmounted immediately), which eliminates the stuck-state bug entirely.
  1211→  1211→
  1212→  1212→**Files changed**: `src/app/page.tsx` — removed `AnimatePresence` import and wrapper, kept `motion.div` with `key={view}`.

  1798→  1798→## Task 9 — AI Retry Logic
  1799→  1799→
  1800→  1800→### 1. Retry helper + error classifier (`src/lib/ai.ts` — extended)
  1801→  1801→Added two helpers at the top of `ai.ts`:
  1802→  1802→
  1803→  1803→- `isTransientError(err: unknown): boolean` — classifies an error as retryable. Returns `true` for:
  1804→  1804→  - Our own `AI_TIMEOUT` sentinel (from `withTimeout`)
  1805→  1805→  - Network/transport errors: `timeout`, `timed out`, `network`, `fetch failed`, `econnreset`, `etimedout`, `enotfound`, `socket hang up`, `aborted`, `und_err_` (undici codes), `retry` (provider-side hint)
  1806→  1806→  - 5xx HTTP status errors from the upstream provider (regex `/\b5\d{2}\b/` + `lower.includes("status")`)
  1807→  1807→  - Defaults to `false` for anything else (so deterministic failures like JSON parse, 4xx auth/quota, unknown errors fail fast instead of compounding)
  1808→  1808→- `withRetry<T>(fn, retries = 1): Promise<T>` — wraps an async fn, retries once on transient errors, waits 500ms between attempts (`RETRY_DELAY_MS = 500`). On each retry attempt it writes a fire-and-forget `AuditEvent` row:
  1809→  1809→
  1810→  1810→```ts
  1811→  1811→void db.auditEvent.create({
  1812→  1812→  data: { category: "ai", action: "retry", level: "warn",
  1813→  1813→          message: `AI call failed, retrying: ${message}` }
  1814→  1814→}).catch(() => { /* swallow logging failures */ });
  1815→  1815→```
  1816→  1816→
  1817→  1817→### 2. Wrapped AI call inside `chatJSON`
  1818→  1818→The original `chatJSON` had one try/catch wrapping both the network call AND the JSON parse. This conflated transient failures with deterministic model-output failures. Restructured into two phases:
  1819→  1819→
  1820→  1820→- **Phase 1 (retryable)**: `ZAI.create()` + `withTimeout(zai.chat.completions.create(...))` are wrapped in a small async closure and passed to `withRetry()`. If this still fails after retry, return the fallback — no JSON parsing attempted.
  1821→  1821→- **Phase 2 (deterministic)**: `extractJSON(raw)` + `JSON.parse(jsonStr)` happen in a separate try/catch. Failures here return the fallback WITHOUT triggering a retry — a model that produced malformed JSON once will produce it again, so spending another 25s on the same prompt would just waste user time.
  1822→  1822→
  1823→  1823→Total worst-case time before fallback: `25s (initial timeout) + 500ms (backoff) + 25s (retry timeout) = 50.5s`. Confirmed by the dev log: `POST /api/analyze 200 in 43s` — the retry actually fired on a real `AI_TIMEOUT` and recovered on the second attempt.
