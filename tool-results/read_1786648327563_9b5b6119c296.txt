   323→## Project Overview
   324→
   325→HIREMIND AI is an AI-powered recruitment assistant (Smart Resume Parser & Mock Interviewer). Core intelligence loop:
   326→
   327→```
   328→RESUME + TARGET JOB
   329→   -> CANDIDATE INTELLIGENCE
   330→   -> SEMANTIC JOB MATCH (Prototype Job Match Index)
   331→   -> SKILL GAP INTELLIGENCE
   332→   -> GAP-DRIVEN ADAPTIVE INTERVIEW  (THE WOW FEATURE)
   333→   -> ANSWER EVALUATION
   334→   -> COMPETENCY STATE UPDATE
   335→   -> JOB READINESS (Prototype Job Readiness Index)
   336→   -> PERSONALIZED IMPROVEMENT ROADMAP
   337→```
   338→
   339→Design philosophy: Apple-inspired premium UX (clean / sleek / minimal / premium / human). Light-first, warm-neutral background, charcoal text, restrained accent.
   340→
   341→Tech stack: Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 + shadcn/ui + Prisma (SQLite) + z-ai-web-dev-sdk (LLM) + Zustand + Framer Motion.
   342→
   343→Critical principles:
   344→- AI understands. Application logic decides. Deterministic scoring.
   345→- Distinguish KNOWN / WEAK / UNKNOWN evidence. Never treat absence as proof of missing skill.
   346→- Adaptive interview: next question MUST depend on previous answer (the demo's WOW moment).
   347→- Demo mode must work reliably end-to-end (10+ consecutive runs).
   348→- Prototype-labeled indices (never "hiring probability").

   953→## Critical Bug Fix
   954→
   955→### AnimatePresence mode="wait" stuck at opacity:0 (CRITICAL)
   956→
   957→**Symptom**: When navigating to a view via `hydrateSession` (e.g., clicking a session in SessionHistory, or loading a URL with `#view=match&session=...`), the store correctly updated `view` to the target view, but the DOM showed the OLD view at `opacity: 0` — the motion.div was stuck in the EXIT state and the new view never mounted.
   958→
   959→**Root cause**: Framer Motion v12's `AnimatePresence` with `mode="wait"` has a bug where the exit animation completes (opacity reaches 0) but the exiting component never unmounts, and the new component never mounts. This was triggered specifically by the async `hydrateSession` flow — the view change happened after an `await fetch()`, which may have caused a timing issue with Framer Motion's internal state tracking.
   960→
   961→**Fix**: Replaced `<AnimatePresence mode="wait">` with a plain `<motion.div key={view}>` (no AnimatePresence wrapper). The `key={view}` forces React to unmount the old content and mount the new content immediately when the view changes. The `initial`/`animate` props provide a smooth fade+slide entrance animation. No exit animation (the old content is unmounted immediately), which eliminates the stuck-state bug entirely.
   962→
   963→**Files changed**: `src/app/page.tsx` — removed `AnimatePresence` import and wrapper, kept `motion.div` with `key={view}`.

  1549→## Task 9 — AI Retry Logic
  1550→
  1551→### 1. Retry helper + error classifier (`src/lib/ai.ts` — extended)
  1552→Added two helpers at the top of `ai.ts`:
  1553→
  1554→- `isTransientError(err: unknown): boolean` — classifies an error as retryable. Returns `true` for:
  1555→  - Our own `AI_TIMEOUT` sentinel (from `withTimeout`)
  1556→  - Network/transport errors: `timeout`, `timed out`, `network`, `fetch failed`, `econnreset`, `etimedout`, `enotfound`, `socket hang up`, `aborted`, `und_err_` (undici codes), `retry` (provider-side hint)
  1557→  - 5xx HTTP status errors from the upstream provider (regex `/\b5\d{2}\b/` + `lower.includes("status")`)
  1558→  - Defaults to `false` for anything else (so deterministic failures like JSON parse, 4xx auth/quota, unknown errors fail fast instead of compounding)
  1559→- `withRetry<T>(fn, retries = 1): Promise<T>` — wraps an async fn, retries once on transient errors, waits 500ms between attempts (`RETRY_DELAY_MS = 500`). On each retry attempt it writes a fire-and-forget `AuditEvent` row:
  1560→
  1561→```ts
  1562→void db.auditEvent.create({
  1563→  data: { category: "ai", action: "retry", level: "warn",
  1564→          message: `AI call failed, retrying: ${message}` }
  1565→}).catch(() => { /* swallow logging failures */ });
  1566→```
  1567→
  1568→### 2. Wrapped AI call inside `chatJSON`
  1569→The original `chatJSON` had one try/catch wrapping both the network call AND the JSON parse. This conflated transient failures with deterministic model-output failures. Restructured into two phases:
  1570→
  1571→- **Phase 1 (retryable)**: `ZAI.create()` + `withTimeout(zai.chat.completions.create(...))` are wrapped in a small async closure and passed to `withRetry()`. If this still fails after retry, return the fallback — no JSON parsing attempted.
  1572→- **Phase 2 (deterministic)**: `extractJSON(raw)` + `JSON.parse(jsonStr)` happen in a separate try/catch. Failures here return the fallback WITHOUT triggering a retry — a model that produced malformed JSON once will produce it again, so spending another 25s on the same prompt would just waste user time.
  1573→
  1574→Total worst-case time before fallback: `25s (initial timeout) + 500ms (backoff) + 25s (retry timeout) = 50.5s`. Confirmed by the dev log: `POST /api/analyze 200 in 43s` — the retry actually fired on a real `AI_TIMEOUT` and recovered on the second attempt.
