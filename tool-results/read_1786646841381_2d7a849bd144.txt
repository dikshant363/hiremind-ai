   133→## Project Overview
   134→
   135→HIREMIND AI is an AI-powered recruitment assistant (Smart Resume Parser & Mock Interviewer). Core intelligence loop:
   136→
   137→```
   138→RESUME + TARGET JOB
   139→   -> CANDIDATE INTELLIGENCE
   140→   -> SEMANTIC JOB MATCH (Prototype Job Match Index)
   141→   -> SKILL GAP INTELLIGENCE
   142→   -> GAP-DRIVEN ADAPTIVE INTERVIEW  (THE WOW FEATURE)
   143→   -> ANSWER EVALUATION
   144→   -> COMPETENCY STATE UPDATE
   145→   -> JOB READINESS (Prototype Job Readiness Index)
   146→   -> PERSONALIZED IMPROVEMENT ROADMAP
   147→```
   148→
   149→Design philosophy: Apple-inspired premium UX (clean / sleek / minimal / premium / human). Light-first, warm-neutral background, charcoal text, restrained accent.
   150→
   151→Tech stack: Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 + shadcn/ui + Prisma (SQLite) + z-ai-web-dev-sdk (LLM) + Zustand + Framer Motion.
   152→
   153→Critical principles:
   154→- AI understands. Application logic decides. Deterministic scoring.
   155→- Distinguish KNOWN / WEAK / UNKNOWN evidence. Never treat absence as proof of missing skill.
   156→- Adaptive interview: next question MUST depend on previous answer (the demo's WOW moment).
   157→- Demo mode must work reliably end-to-end (10+ consecutive runs).
   158→- Prototype-labeled indices (never "hiring probability").

   763→## Critical Bug Fix
   764→
   765→### AnimatePresence mode="wait" stuck at opacity:0 (CRITICAL)
   766→
   767→**Symptom**: When navigating to a view via `hydrateSession` (e.g., clicking a session in SessionHistory, or loading a URL with `#view=match&session=...`), the store correctly updated `view` to the target view, but the DOM showed the OLD view at `opacity: 0` — the motion.div was stuck in the EXIT state and the new view never mounted.
   768→
   769→**Root cause**: Framer Motion v12's `AnimatePresence` with `mode="wait"` has a bug where the exit animation completes (opacity reaches 0) but the exiting component never unmounts, and the new component never mounts. This was triggered specifically by the async `hydrateSession` flow — the view change happened after an `await fetch()`, which may have caused a timing issue with Framer Motion's internal state tracking.
   770→
   771→**Fix**: Replaced `<AnimatePresence mode="wait">` with a plain `<motion.div key={view}>` (no AnimatePresence wrapper). The `key={view}` forces React to unmount the old content and mount the new content immediately when the view changes. The `initial`/`animate` props provide a smooth fade+slide entrance animation. No exit animation (the old content is unmounted immediately), which eliminates the stuck-state bug entirely.
   772→
   773→**Files changed**: `src/app/page.tsx` — removed `AnimatePresence` import and wrapper, kept `motion.div` with `key={view}`.

  1361→### 1. Retry helper + error classifier (`src/lib/ai.ts` — extended)
  1362→Added two helpers at the top of `ai.ts`:
  1363→
  1364→- `isTransientError(err: unknown): boolean` — classifies an error as retryable. Returns `true` for:
  1365→  - Our own `AI_TIMEOUT` sentinel (from `withTimeout`)

  1369→- `withRetry<T>(fn, retries = 1): Promise<T>` — wraps an async fn, retries once on transient errors, waits 500ms between attempts (`RETRY_DELAY_MS = 500`). On each retry attempt it writes a fire-and-forget `AuditEvent` row:
  1370→
  1371→```ts

  1373→  data: { category: "ai", action: "retry", level: "warn",
  1374→          message: `AI call failed, retrying: ${message}` }
  1375→}).catch(() => { /* swallow logging failures */ });
  1376→```
  1377→
  1378→### 2. Wrapped AI call inside `chatJSON`
  1379→The original `chatJSON` had one try/catch wrapping both the network call AND the JSON parse. This conflated transient failures with deterministic model-output failures. Restructured into two phases:
  1380→
  1381→- **Phase 1 (retryable)**: `ZAI.create()` + `withTimeout(zai.chat.completions.create(...))` are wrapped in a small async closure and passed to `withRetry()`. If this still fails after retry, return the fallback — no JSON parsing attempted.
  1382→- **Phase 2 (deterministic)**: `extractJSON(raw)` + `JSON.parse(jsonStr)` happen in a separate try/catch. Failures here return the fallback WITHOUT triggering a retry — a model that produced malformed JSON once will produce it again, so spending another 25s on the same prompt would just waste user time.
  1383→
  1384→Total worst-case time before fallback: `25s (initial timeout) + 500ms (backoff) + 25s (retry timeout) = 50.5s`. Confirmed by the dev log: `POST /api/analyze 200 in 43s` — the retry actually fired on a real `AI_TIMEOUT` and recovered on the second attempt.
